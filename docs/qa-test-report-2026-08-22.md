## 详细发现

### [BUG-001] 登录接口无暴力破解 / 限流防护
- **维度**：维度二·2C.2 / 维度五·5.5
- **严重程度**：🔴 Critical
- **测试用例**：连续 20 次错误密码登录 + 100 次并发 `GET /api/devices`（携带合法 token）
- **复现步骤**：
  1. `for i in 1..20: POST /api/auth/login {admin, wrongpass$i}` → 全部 401
  2. 100 路并发 `GET /api/devices` → 状态码全部 200，无 429
  3. 之后用正确密码登录 → 仍 201 成功
- **预期结果**：连续失败应触发锁定 / 验证码 / 429 限流
- **实际结果**：无任何频率限制、锁定或验证码机制
- **证据**：`curl` 批量返回均为正常状态码，无 `Retry-After` / `429`
- **建议修复**：在 `/api/auth/login` 增加基于 IP + 账号的失败计数与指数退避限流（如 5 次失败锁定 15 分钟 / 触发验证码）；对高频 API 加全局 Rate Limit 中间件（如 `@nestjs/throttler`）。

### [BUG-002] 全站明文 HTTP，无 TLS / HSTS 无效
- **维度**：维度五·5.6（🔴 Critical）
- **严重程度**：🔴 Critical
- **测试用例**：`curl http://121.43.230.202:3000/` → 200，无 301 跳转；响应含 `Strict-Transport-Security` 但站点本身为 HTTP
- **预期结果**：生产环境应全站 HTTPS，HTTP 301 跳转，TLS≥1.2，有效 HSTS
- **实际结果**：仅 HTTP（端口 3000）；无证书；HSTS 头在 HTTP 下无意义
- **证据**：`curl -I` 显示 `HTTP/1.1 200 OK` 且无 `Location` 跳转；无 `https://` 入口
- **建议修复**：前置反向代理/Nginx 启用 TLS 1.2+，HTTP→HTTPS 301，配置有效 HSTS；演示环境至少标注为不安全。

### [BUG-003] 登出（退出登录）功能失效
- **维度**：维度二·2C.4（🟠 Major）
- **严重程度**：🟠 Major
- **测试用例**：在已登录 `/devices` 页点击"退出登录"（`@e22`）两次 + 硬刷新后再次点击
- **复现步骤**：
  1. 登录态访问 `/devices`（显示设备态势总览）
  2. 点击侧边栏"退出登录"
  3. 页面仍停留在 `/devices` 且显示完整设备内容
  4. `curl -H "Authorization: Bearer <旧token>" /api/devices` → 仍 200
- **预期结果**：清除会话并重定向至 `/login`，旧 token 客户端失效
- **实际结果**：点击无效果，仍保持在已认证状态
- **证据**：bsk 快照仍显示 `@e22 button "退出登录"` 与 `heading "设备态势总览"`；API 旧 token 有效
- **建议修复**：核查登出处理函数是否正确清除内存 token / localStorage / 调用 `/api/auth/logout`；当前疑似事件未绑定或清状态逻辑缺失。

### [BUG-004] "新增设备"对话框无法关闭（ESC/取消均无效）
- **维度**：维度三·3.10（🟠 Major）
- **严重程度**：🟠 Major
- **测试用例**：设备中心 → "新增设备" → 按 ESC；再次打开 → 点击"取消"
- **复现步骤**：
  1. 打开"新增设备"对话框（正常）
  2. 按 `Escape` → 对话框仍在（modal cover=100%）
  3. 点击"取消"按钮 `@e9` → 对话框仍在
  4. 仅硬刷新页面可关闭
- **预期结果**：ESC 与取消按钮均可关闭模态框，背景可恢复滚动
- **实际结果**：对话框无法关闭，阻塞后续操作
- **证据**：bsk 快照 `dialog "新增设备"` 持续存在；`press Escape` 返回 ok 但 UI 不变
- **建议修复**：为对话框绑定 `Escape` 键处理与取消回调；检查是否被某个全局拦截或 focus trap 死锁。

### [BUG-005] 静态资源未启用 Gzip/Brotli 压缩
- **维度**：维度四·4.5（🟠 Major）
- **严重程度**：🟠 Major
- **测试用例**：`curl -H 'Accept-Encoding: gzip, deflate, br' /assets/index.standalone-*.js`
- **预期结果**：返回 `Content-Encoding: br` 或 `gzip`
- **实际结果**：无任何 `Content-Encoding`；600KB JS / 209KB CSS 以明文传输
- **证据**：响应头无压缩字段；`Content-Length: 611701`
- **建议修复**：在 Nginx / NestJS 静态服务启用 Brotli/Gzip；预计 600KB JS 可压缩至 ~180KB，显著改善慢网首屏。

### [BUG-006] API 分页参数被完全忽略
- **维度**：维度六·6.4 / 维度四·4.7（🟠 Major）
- **严重程度**：🟠 Major
- **测试用例**：`GET /api/devices?limit=1`、`?limit=99999`、`?page=99999`、`?offset=1000`、`?pageSize=1`
- **复现步骤**：分别请求上述参数，对比响应体大小
- **预期结果**：分页生效，返回子集
- **实际结果**：所有参数返回相同体积（8755B 全量）；疑似未实现服务端分页
- **证据**：curl 各参数 `size` 完全一致
- **建议修复**：实现服务端 `limit/offset` 分页；前端长列表配合虚拟滚动，避免一次性拉取万级数据。

### [BUG-007] Secure Cookie 与 HTTP 部署相矛盾
- **维度**：维度五·5.5（🟠 Major）
- **严重程度**：🟠 Major
- **测试用例**：登录响应头 `Set-Cookie: ewoh_refresh_token=...; HttpOnly; SameSite=Strict; Secure`
- **预期结果**：若站点为 HTTP，则不应标记 `Secure`（否则浏览器永不发送该 Cookie）
- **实际结果**：站点为 HTTP，但刷新令牌 Cookie 带 `Secure` → 在 HTTP 下该 Cookie 形同虚设，刷新机制失效
- **证据**：登录响应头见 `Secure` 标志；站点无 TLS
- **建议修复**：先解决 TLS（BUG-002），Secure Cookie 方才有效；否则移除 Secure 或改用内存刷新。

### [BUG-008] 创建设备失败且错误提示不清晰
- **维度**：维度二·2B.1（🟠 Major）
- **严重程度**：🟠 Major
- **测试用例**：设备中心 → "新增设备" → 填写合法 `设备ID=EXO-TESTQA001` + `型号` → 保存
- **预期结果**：设备出现在列表
- **实际结果**：返回"保存失败"，对话框保留；`POST /api/devices` → 404（路由无 POST 处理器）
- **证据**：UI 显示"保存失败"；API 直接 `POST /api/devices` 返回 `Cannot POST /api/devices` 404
- **建议修复**：定位真实创建设备端点（前端为客户端生成式调用，未能从 bundle 直接定位）；确认是否因演示环境"未接入数据源"导致；返回结构化字段错误而非笼统"保存失败"。

### [BUG-009] 异常请求体返回 500 而非 4xx
- **维度**：维度五·5.3 / 5.8 / 维度六·6.2（🟠 Major）
- **严重程度**：🟠 Major
- **测试用例**：
  - 登录体含对象 `{"username":{"$ne":null}}` → 500
  - 11MB 登录体 → 500
- **预期结果**：非法类型应 400；超大 payload 应 413
- **实际结果**：均返回 500 `服务器内部错误`（未妥善处理，存在 DoS/信息面风险）
- **证据**：curl 返回 `INTERNAL_ERROR`；虽无详情泄露，但不应为 500
- **建议修复**：全局异常过滤器对 `PayloadTooLarge` 返回 413；对反序列化/校验异常返回 400；设置请求体大小上限（`body-parser` limit）。

### Minor 级发现
- **[MIN-001] 未知路由 HTTP 状态为 200（1.3）**：`/this-does-not-exist-xyz` 服务端返回 SPA 壳（200），虽客户端渲染了友好 404 页（"404 页面不存在或已被移动"），但 HTTP 语义应为 404。建议服务端对未知 UI 路由返回 404 状态码。
- **[MIN-002] 缺少 meta description（1.7）**：首页 `<head>` 仅有 `<title>`，无 `<meta name="description">`，不利于 SEO/可访问性。
- **[MIN-003] 静态资源 Cache-Control max-age=0（4.4）**：JS/CSS 带 `ETag` 但 `Cache-Control: public, max-age=0`，每次访问需重新协商；建议对带 hash 的静态资源设长缓存（如 `max-age=31536000, immutable`）。
- **[MIN-004] 创建表单错误定位不足（2A.3）**：空提交显示"请填写设备ID"字段错误（良好），但非法设备 ID（如 XSS 串）被静默拦截、无明显提示，且"保存失败"未指向具体字段。
- **[MIN-005] `/api` 根路径返回 200（2C.5 边界）**：`GET /api` 返回 200（错误列表体），其余 58 个 API 前缀均正确返回 401/404，无越权数据泄露。
- **[MIN-006] 前进/后退自动化超时（1.5）**：SPA 客户端路由正常（点击导航 URL 正确切换），但自动化 `navigate-back/forward` 命令多次超时（应用较重 + 工具 RPC 超时），建议人工复核浏览器后退键行为。
- **[MIN-007] 登录无可见防重复提交态（2A.2）**：提交时未见明确的 loading/disabled 态观测；需结合代码确认防重复提交。
- **[MIN-008] favicon.ico 回退为 HTML（1.8）**：`/favicon.ico` 返回 text/html（SPA 兜底），但页面显式引用 `/favicon.svg`（正常返回 image/svg+xml），故实际 favicon 正常。
- **[MIN-009] 未验证返回原页面（2C.3）**：未登录访问受保护页正确重定向至 `/login`（鉴权守卫有效），但登录后是否自动跳回原页面未验证。

## 风险评估与优先修复建议（Top 5）
1. **【最高优先级·安全】登录限流（BUG-001）+ 全站 HTTPS（BUG-002）**：演示环境暴露公网 IP + 明文 HTTP + 无暴力破解防护，账号面临被撞库/爆破风险。立即前置 TLS 并加登录限流。
2. **【核心功能】登出失效（BUG-003）**：用户无法退出，存在会话滞留与多用户设备安全风险；属 P0 功能缺陷。
3. **【核心功能】模态框无法关闭（BUG-004）**：任何打开"新增设备"的用户将被卡死，必须刷新才能恢复，严重影响可用性。
4. **【性能·安全面】启用压缩 + 服务端分页（BUG-005/006）**：600KB 未压缩 JS 在慢网下首屏极慢；无分页的 API 在大数据量下易超时/内存膨胀。
5. **【健壮性】异常请求体返回 500（BUG-009）+ Secure Cookie 矛盾（BUG-007）**：统一异常为 4xx、设请求体上限，并修正 Cookie 安全属性与部署协议的匹配。
