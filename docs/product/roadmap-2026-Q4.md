## 0. 执行摘要

当前状态一句话：**J1 已交付但价值未验证，J2 被 Gate 阻塞，同时工程复核陆续暴露出若干存量缺陷。**

本季度的第一优先级**不是做新功能**，而是两件事：

1. **补上价值验证**（埋点基线 + 用户访谈）——它阻塞 J2，也决定"对象中心"范式是否值得继续投入；
2. **修掉已确认的存量缺陷**——尤其是告警角色盲区（用户点击必 400），这是每天都在发生的真实故障。

## 1. 排序方法与依据

采用**影响 × 收益矩阵**为主，叠加**阻塞关系**与**成本**三视角。

| 维度 | 说明 |
|------|------|
| 影响 | 用户触及面 × 问题严重度（故障 > 效率损耗 > 观感） |
| 收益 | 相对成本的产出（含"是否解锁后续工作"） |
| 阻塞 | 该项是否卡住其他任务 |
| 成本 | 工程估算（d = 人天） |

### ⚠️ 数据诚实声明

| 声明 | 内容 |
|------|------|
| **无用户行为数据** | 全部"影响"评分基于**代码证据推导 + 角色使用路径推断**，**非**真实使用统计。EWOH 当前无页面跳转与任务完成埋点。 |
| **无访谈数据** | 全部"痛点"未经真实用户验证。研究方案已就绪（见 §2 A2），执行后须回校本路线图。 |
| **成本为估算** | 由代码改动面估算，未经过工程排期确认。 |

> 因此本路线图是**当前信息下的最优判断**，不是定论。
> A1/A2 完成后应立即回校——这正是把它们排在 Now 首位的理由。

### A-1 · B1 告警角色盲区修复（1d）

**问题**：`/alerts` 列表页按状态渲染动作按钮，但后端按角色校验，
不匹配则返回 400。用户**看到按钮、点了必错**。

**⚠️ 勘误（2026-09-01）**：初版称「device_ops 点 open 的确认必 400」——**该例不成立**。
`handler = { dispatcher, workshop_lead, device_ops }`，三者皆可确认 `open`。
真实的三处表现是：

| # | 场景 | 旧前端 | 后端 | 结果 |
|---|------|--------|------|------|
| ① | `safety_admin` 看 `open`/`acknowledged`/`processing` | 显示确认/处置/关闭 | `safety_admin` ∉ `handler` | **必 400** |
| ② | 非 `safety_admin` 看 `closed` | 显示「重开」 | `reopen` 需 `safety_admin` | **必 400** |
| ③ | 任意 handler 看 `reopened` | 只显示「确认」 | 有 2 个合法转移 | **漏「处置」** |

证据：`shared/alert-state-machine.ts:13-30`（`handler` 复合角色，
仅 `closed→reopened` 为 `safety_admin` 专属）、`HANDLER_ROLES :32-34`、
原 `Alerts.tsx` 的 `actionFor` 无角色维度且该页全文无角色判断。

**修复方案（关键裁决）**：

> ❌ **不要在前端硬编码角色-动作矩阵**。
> ✅ **调用 `shared/alert-state-machine.ts` 的既有判定函数**——它就是后端正在执行的同一套规则。

```ts
import {
  alertStateTransitionAllowed,
  alertActionToState,
} from '@shared/alert-state-machine';

// 1. 取当前用户角色（与后端 actor.roles 同一口径）
// 2. 对候选 action：alertActionToState(action) → 目标态
// 3. alertStateTransitionAllowed(current, target, role) → 决定是否渲染
// 4. global_admin 单独短路放行（对齐 alert.service.ts:54-56 的服务端行为）
```

**验收标准**：

| # | 标准 |
|---|------|
| V-1 | 用 `shared/alert-state-machine.spec.ts` 的既有用例作为契约——前端渲染结果须与之一致 |
| V-2 | 无角色信息时**不渲染**任何动作按钮（fail-closed，不缺省放行） |
| V-3 | 无可用动作时给出明确说明（如"当前角色无可执行操作"），而非空白或禁用态堆叠 |
| V-4 | `global_admin` 行为与服务端一致（放行全部转移） |
| V-5 | 不改动后端、不改动状态机语义 |

**回归风险**：低。改动限于前端渲染层，判定逻辑复用已有且带 spec 的模块。
主要风险是角色取数口径与后端不一致——建议以 `getAuthUser()?.roles` 与 `OrgContext.roles` 对齐为准。

**范围**：本项修 `/alerts` 列表页（存量）。J2 新建的告警工作台复用同一逻辑，不重复实现。

### A-2 · A1 埋点上线与基线采集（0.5d）

**现状**：`client/src/lib/telemetry.ts` 已实现（内存环形缓冲 + 可插拔 sink，零依赖），
事件覆盖 `object_workbench_view` / `approval_deeplink_click` / `terminal_action_click` / `nav_source`。

**缺什么**：没有一个真实 sink 把事件落到**可查询**的地方。

**建议方案（最小改动）**：
- 复用项目既有的后端日志/审计通道，新增一个轻量事件上报端点；
- 或先落 `localStorage` + 管理端导出（若后端排期紧张，可临时方案，但须能查询）。

> ⚠️ **隐私**：埋点只采集对象类型/ID、动作名、状态与角色（不采集个人信息），
> 沿用既有 operator 口径；GDPR / 个人信息保护法下属最小必要采集。

**验收**：能按天查询 4 个事件的发生次数，支撑 J1 §8 与 J2 §8 的全部指标计算。
