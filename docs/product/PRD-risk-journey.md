## 0. 启动前置条件（Gate）— 原文保留（历史决策依据）

**J2 不应在 J1 价值被验证之前开工。** 这是本文的第一条产品判断。

| Gate | 条件 | 当前状态 | 阻塞级别 |
|------|------|---------|---------|
| **G-1** | J1 埋点上线并采集到 ≥2 周数据，得出真实基线 | ❌ **未达成**：埋点代码已就位（`lib/telemetry.ts`），但**无任何历史基线** | **强阻塞** |
| **G-2** | 完成 3–5 场用户访谈（调度员 / 安全员 / 班组长），验证痛点优先级 | ❌ **未达成**：J1 的全部用户故事均由代码证据推导，**未经真实用户验证**（J1 PRD Q-5） | **强阻塞** |
| G-3 | 核实 `approvePlan` 是否存在发起人回避校验 | ⚠️ 待后端确认（决策单 D-3） | 弱阻塞（不直接阻塞 J2） |

### 为什么设这个 Gate

J1 用约 2 周工时交付了对象工作台、终态出口、流程带等能力，工程验证全绿
（`tsc -b` 0 错误、前端 142 套件/1257 用例、后端 290 套件/2253 用例）。
**但至今无法回答"它让用户更快了吗"**——因为没有任何基线数据。

在这个状态下直接推广 J2，会重现同一个问题：再交付一个无法验证价值的功能。
**先花 2–4 周拿到 J1 的基线与用户反馈，再决定是否沿同一范式扩张，风险最低。**

> 若 G-1/G-2 达成后 J1 指标未达预期（如页面切换次数未下降），
> 说明"对象中心"这一范式本身需要修正——此时投入 J2 会把错误范式复制到第二个域。

## 1. 为什么是 J2（产品判断）

P2 清单有三项：J2 风险旅程、J3 治理旅程、驾驶舱三页收敛。选择 J2：

| 候选 | 用户价值 | 成本 | 依赖 | 判断 |
|------|---------|------|------|------|
| **J2 风险旅程** | **高**：安全域，且完全复用 J1 基础设施 | **低**（复用 JourneyRail / 工作台 / 埋点 / 语义 Token） | G-1、G-2 | ✅ **推荐** |
| J3 治理旅程 | 中：面向低频配置场景 | 中 | 需策略域知识 | 排后 |
| 驾驶舱三页收敛 | 高：降低认知负担 | **高**（指挥地图 4664 行，ALL_ROLES 唯一入口） | 需产品拍板 + 使用数据 | 单独立项 |

**选 J2 的三条理由**：

1. **复用红利最大**。J1 已交付 `JourneyRail`、对象工作台骨架、`resolveObjectRoute`、
   语义 Token、埋点工具——J2 是**同范式的第二个实例**，边际成本远低于 J1。
2. **安全域价值更高**。J1 实施过程中已暴露：审批台实际承载的是 `control_request`
   （高危物理控制指令，**安全关键**）。风险处置链路的可用性 directly 关系到现场安全。
3. **状态机天然吻合**。告警已有完整状态机（发现 → 确认 → 处置 → 关闭/重开），
   与 J2 设想一一对应，不需要设计新流程。

## 2. 执行摘要

### 2.1 背景

J1 解决了"排产方案"这一对象的跨页流转。风险域存在**同构问题**：
告警只有列表页（`app.tsx:94`），没有详情路由，用户看到一条告警后无法下钻查看上下文、
无法跳到关联设备、无法看到处置进展——与 J1 治理前的"派工黑洞"是同一个病。

### 2.2 目标

| 层级 | 目标 | 衡量 |
|------|------|------|
| **业务目标** | 缩短告警从产生到关闭的时长 | 平均处置时长（MTTD/MTTR）（**基线待埋点**） |
| **用户目标** | 从告警一键到达"处置所需的全部上下文" | 告警详情页使用率 ≥ 40% |
| **质量目标** | 消除风险面板与告警列表中的裸 ID | 裸 UUID 归零 |

### 2.3 非目标（Non-goals）

| 不做 | 理由 |
|------|------|
| ❌ 不改告警状态机语义 | `open → acknowledged → processing → closed ⇄ reopened` 保持不变 |
| ❌ 不做告警规则引擎 | 告警的产生逻辑不在本范围 |
| ❌ 不扩展通知渠道 | 推送/通知已由既有模块承载 |
| ❌ 不做 J3 治理旅程 | 待 J2 验证有效后再推广 |
| ❌ 不做驾驶舱三页收敛 | 需产品拍板，单独立项 |
| ❌ 不删除 `/alerts` 列表页 | 列表仍是批量处置的主入口 |

### 2.4 关键现状结论（代码证据）

| # | 结论 | 证据 |
|---|------|------|
| FA-1 | **告警只有列表页，无详情路由**——用户无法下钻 | `app.tsx:94`（仅 `/alerts`，无 `/alerts/:id`） |
| FA-2 | 告警**本身有人类可读标题**，无需对象描述符即可辨识 | `api/alerts.ts:8` `title: string \| null` |
| FA-3 | 告警**只关联设备**（`deviceId`），无人员/工位关联 | `api/alerts.ts:6` |
| FA-4 | 告警状态机完整，与 J2 设想一致 | `Alerts.tsx:5-25`（5 态 + `actionFor` 映射） |
| FA-5 | 风险面板直接展示裸 `risk.id` | `WorkOrchestration/RisksPanel.tsx:48`（`font-mono`） |
| FA-6 | 告警页是"孤岛"（0 出链） | 既有的 23/25 页面零出链结论 |
| FA-7 | J1 基础设施可复用 | `components/app-shell/JourneyRail.tsx`、`resolveObjectRoute()`、`lib/telemetry.ts` |

> **FA-2 与 J1 的关键差异**：调度审批必须引入对象描述符（`ObjectDescriptor`）才能消除裸 UUID，
> 因为审批实例只存了 `entityType`+`entityId`。**告警自带 title，因此 J2 无需后端配合即可达成"可辨识"**——
> 这是 J2 成本显著低于 J1 的主要原因。

## 5. 功能规格要点

### 5.1 RK-1 告警对象工作台

复用 J1 的对象工作台骨架，在 `SUPPORTED_TYPES` 中接入 `alert`。

| 区域 | 内容 | 数据来源 |
|------|------|---------|
| 流程带 | 5 态派生（见 §5.2） | `status` |
| 头部 | 告警标题 + 严重度徽章 + 状态徽章 | `title`、`severity`、`status` |
| 元信息 | 产生时间 · 关联设备（可下钻）· 严重度 | `createdAt`、`deviceId`、`severity` |
| 动作区 | **当前状态 × 当前用户角色**允许的转移动作 | `shared/alert-state-machine.ts`（见下方裁决） |
| 视图区 | 概览 / 关联对象 / 状态历史 / 证据 | 概览需后端提供告警详情，见 Q-R1 |

> **关键裁决（v1.1 修正，工程评估 E-1）**：
> **不要复用 `Alerts.tsx:15-25` 的 `actionFor`**——它只按状态返回动作，**完全不感知角色**，
> 而后端状态机是**角色感知 + fail-closed**的（`shared/alert-state-machine.ts`，ADR-031 单一事实源）：
>
> | 转移 | 允许角色 |
> |------|---------|
> | `open → acknowledged` | **`handler`** |
> | `acknowledged → processing` | **`handler`** |
> | `processing → closed` | **`handler`** |
> | `closed → reopened` | **仅 `safety_admin`** |
> | `reopened → acknowledged` / `→ processing` | **`handler`**（两个合法转移） |
> | 任何转移 | 无角色 → **拒绝** |
>
> **`handler` = `{ dispatcher, workshop_lead, device_ops }`**（`HANDLER_ROLES`）。
> **只有 `reopen` 是 `safety_admin` 专属**，其余三者皆可执行。
>
> > ⚠️ 勘误：初版误写为每个转移对应一个专属角色（把 spec 的示例用例当成排他规则），已修正。
>
> 因此直接复用会产生三处缺陷（详见 `PRD-risk-journey-dev-feasibility.md` §2 E-1）：
> ① `safety_admin` 看到确认/处置/关闭按钮但点击必 400；
> ② 非 `safety_admin` 点「重开」必 400；
> ③ `reopened` 态漏掉「处置」入口。
>
> **正确做法**：复用 `shared/alert-state-machine.ts` 的
> `alertActionToState(action)` + `alertStateTransitionAllowed(current, target, role)`，
> 按「状态 × 角色」过滤后渲染；`global_admin` 单独短路放行（对齐 `alert.service.ts:54-56`）。
> 该模块位于 `shared/` 且有 spec，**前端可直接 import，无需后端配合**。
> 这仍满足"避免第二套实现"——因为它复用的是**后端正在执行的同一套规则**。
>
> ✅ **存量部分已修复并合入**（2026-09-01）：`pages/Alerts/alertActions.ts` +
> `Alerts.tsx` 接入 + `alertActions.test.ts`（13 例），全量验证通过。
> J2 新建的告警工作台**直接复用同一模块**，不重复实现。

### 5.2 RK-2 告警流程带

由 `status` 派生，与 J1 的 `planJourney` 同构：

| 环节 | `open` | `acknowledged` | `processing` | `closed` | `reopened` |
|------|--------|----------------|--------------|----------|-----------|
| 发现 | done | done | done | done | done |
| 确认 | **current** | done | done | done | **current** |
| 处置 | todo | **current** | done | done | todo |
| 关闭 | todo | todo | **current** | done | todo |

- `closed` 为终态，全部 done；
- `reopened` 视为回到「确认」环节（流程重新启动）。

### 5.3 RK-4 关联设备下钻

直接复用 J1 已实现的 `resolveObjectRoute('device', id)` → `/devices`。
无需新增代码，仅需在工作台关联对象区调用。

### 5.4 RK-5 风险面板去裸 ID

`RisksPanel.tsx:48` 当前渲染 `risk.id`。
✅ **Q-R2 已消解（2026-09-01 设计核查）**：`WorkRisk` 接口**有 `title` 字段**
（`api/work.ts:71-79`：id/title/severity/likelihood/trigger/owner/mitigation/status）——
裸 ID 纯粹是前端没用它。**按有名称分支执行**：主显 `risk.title`，`id` 降为等宽小字辅助信息，零后端改动。

| 健康 | 误报率 | 待埋点 | 不上升 |
