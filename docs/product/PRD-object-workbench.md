### 两处实现裁决（与 v1.1 文档的差异，均已评估）

1. **OD-6 采用派生而非后端落库字段**（原计划后端 +1d → 实际 0）。
   理由：`narrationStatus` 落库需改 shared 契约 + plan 落库 + narrator 三处状态流转，
   且引入状态同步问题（失败重试、方案重算时的重置）。派生方案零后端依赖，
   已能覆盖真实体验缺口（此前未生成时整块不渲染＝永久空白）。
   详见 `client/src/lib/narration.ts` 文件头注释。
2. **工作台头部采用替代方案**（评估报告 §8.3）：`SchedulingPlanV2` 无「责任人」「数据来源」字段，
   改用 `solverStatus` / `fallbackReason` / `violations`，未新增后端依赖。
3. **OD-8 流程环节由状态派生，不新增持久状态**：`planJourney(status, narrationStatus, planId)`
   是 `PlanStatus` 的投影，因此不存在"流程带与真实状态脱节"的可能，也不需要后端配合。
4. **OD-9 下钻复用既有页面，不新建页面**：`scheduling_plan` → 对象工作台，
   `device` → `/devices`，`person` → `/personnel`，`station` 无对应页面故渲染纯文本（不产生死链）。

## 1. 为什么是这个功能（产品判断）

需求方提出"写一份新功能的 PRD"但未指定功能。基于前序 UX 架构与 UI 设计审计，候选有三，本文选择 **A**：

| 候选 | 用户价值 | 工程成本 | 前置依赖 | 判断 |
|------|---------|---------|---------|------|
| **A. 对象工作台 + 对象描述符** | **高**：同时闭合 4 个已确认断点 | 中 | 后端约 1.5d | ✅ **推荐** |
| B. 状态色板收敛（368 处） | 中：视觉一致 + 三主题生效，但**不产生新能力** | 中低 | 无 | 技术债单独立项 |
| C. 驾驶舱三页收敛 | 高：降低认知负担 | **高**（指挥地图 4664 行，ALL_ROLES 唯一入口） | 需产品拍板 + 使用数据 | 暂缓 |

**选 A 的三个理由**：

1. **唯一能同时闭合多个断点的杠杆**：UX 审计确认 8 个断点（B1–B8），A 直接闭合 B1（页面群岛）、B2（裸 UUID）、B3（内容与流程割裂）、B4（终态无出口）。
2. **B 与 C 的公共前置**：对象描述符契约一旦建立，色板收敛与驾驶舱收敛都获得统一渲染数据源。
3. **成本可控可灰度**：核心后端改动落在 JSON 列加一个可选字段，**无 DB 迁移、老数据天然兼容**。

> 工程审查结论：**技术前提 11 项中 5 项成立、3 项错误、2 项阻塞、1 项需澄清**。
> 三项错误已在 v1.1 修正（C-1/C-4/C-6），两项阻塞已转化为明确后端任务（C-7）与实现澄清（C-8）。
> **无一项推翻产品判断。**

## 2. 执行摘要

### 2.1 背景

EWOH 以**页面**为单元组织产品（20 个平级页面 + 侧边栏切换），而工厂调度业务以**对象**
（控制指令 / 任务 / 危险作业 / 调度方案 / 设备 / 人员）为单元流转。用户被迫充当"页面之间的人肉集成层"。

### 2.2 目标

| 层级 | 目标 | 衡量方式 |
|------|------|---------|
| **业务目标** | 缩短从"发现需要处理"到"处理完成"的端到端时长 | 跨页面任务完成时长（**基线待埋点**） |
| **用户目标** | 用户跟随对象流转，而非在页面间迷路 | 单任务页面切换次数下降 ≥ 40% |
| **质量目标** | 消除"看不懂在批什么"的审批体验 | 审批台裸 UUID 归零 |

### 2.3 非目标（Non-goals，工程请勿越界实现）

| 不做 | 理由 |
|------|------|
| ❌ 不改业务状态机 | 方案/工单/审批的状态跃迁语义一律不动 |
| ❌ 不改权限矩阵 | 沿用 `lib/navigation.ts` 既有 `roles` 配置 |
| ❌ 不动调度求解器 | 算法、约束、评分完全不在范围内 |
| ❌ 不把调度方案接入会签系统 | 涉及流程治理与 fail-closed 白名单扩展，单独立项（§10 Q-7） |
| ❌ 不做驾驶舱三页收敛 | 需产品拍板，单独立项 |
| ❌ 不做色板 368 处收敛 | 技术债单独立项，避免稀释价值验证 |
| ❌ 不删除任何现有页面或路由 | 本功能是**增量**，旧路径保留为别名 |

### 2.4 关键现状结论（v1.1 已修正）

| # | 结论 | 证据 |
|---|------|------|
| F-1 | **25 个页面目录中 23 个路由出链数为 0** | `pages/` 全量检索 |
| F-2 | 数据驱动下钻能力**已存在但未推广** | `WorkbenchList.tsx:78-90`、`:227` |
| F-3 | 审批台显示**裸 UUID**，且标签误导 | `approvalConsoleLogic.ts:47-48` |
| F-4 | 根因：审批只存 `entityType`+`entityId` 于 `evidenceJson`，无展示字段快照 | **`approval-persistence.service.ts:206-212`**（v1.0 误引已废弃的 `approval.service.ts`） |
| F-5 | 方案进入终态后**仅剩一行静态文本** | `Scheduling.tsx:291-304` |
| F-6 | 异步产物无 pending 态 | `Scheduling.tsx:184` |
| F-7 | 指标以 `JSON.stringify` 直出 | `Scheduling.tsx:195-197` |

## 5. 功能规格要点

### 5.1 OD-1 对象描述符契约（后端，C-1/C-4 已修正）

```ts
interface ObjectDescriptor {
  objectType: 'task' | 'dangerous_action' | 'control_request';  // 必须对齐 APPROVAL_ROLE_POLICY
  objectId: string;
  title: string;                                  // 人类可读标题，替代裸 UUID
  summary?: string;                               // 一句话摘要
  status?: string;
  metrics?: Record<string, number | string>;
  requestedBy?: string;
  deepLink: string;                               // 前端路由
}
```

| 项 | 规格 |
|----|------|
| **落点** | `approval-persistence.service.ts:155` `createApproval` → `evidenceJson`（`:206-212`） |
| **读取** | `listPending`（`:145-151`）返回值增加 `subject: evidence.subject ?? null` |
| **迁移** | **无需 DB 迁移**（`evidenceJson` 为 JSON 列） |
| **兼容** | 老数据无 `subject` → `?? null` → 前端回退现状文案 |
| **附带** | `:193` 落库标题 `Approval for ${entityType} ${entityId}` 一并改为 `subject.title ?? 现状` |
| **扩展** | 新增对象类型须同步在 `APPROVAL_ROLE_POLICY`（`:38-46`）登记（fail-closed，X-7） |

> **验收铁律**：审批台用户可见区域不得出现 32/36 位十六进制串。

### 5.2 OD-2 / OD-3 对象路由与工作台骨架

路由：`/o/:objectType/:objectId`，**首批接 `scheduling_plan`**（`getPlan` API 已就绪，`api/scheduler.ts:139`）。

```
┌─ 对象头部 ─────────────────────────────────────────┐
│ 标题（人类可读，禁止裸 UUID） [状态徽章]  [状态机允许的动作] │
│ 对象 ID（等宽字体）· v版本                            │
│ 责任人 · 触发源 · 更新时间 · 数据来源徽章              │
├─ Tabs ────────────────────────────────────────────┤
│ 概览 | 关联对象 | 状态历史 | 证据      （URL 同步）    │
└───────────────────────────────────────────────────┘
```

> **注意**：工作台首批对象（`scheduling_plan`）与描述符首批服务对象（`control_request` 等）
> **可以不同**——两者通过契约关联，但落地节奏解耦，互不阻塞。

### 5.3 OD-5 终态行动条（C-8 已澄清）

| 方案状态（`PlanStatus` 8 态之一） | 主行动 | 次行动 | 回溯 |
|---|---|---|---|
| `approved` | 下发执行 | 重新排程 | 对比其他方案 |
| `dispatched` / `executing` | **查看执行态势** | 触发重排 | 复制方案 ID |
| `completed` | 查看执行报告 | 结案复盘 | 导出 KPI |
| `rejected` | 查看驳回理由 | 重新排程 | 查看决策历史 |
| **`superseded` 或 409 分支** | **重新计算** | 查看变更详情 | 查看决策历史 |

> ⚠️ **「已过期」不是 `row.status` 的取值**（PlanStatus 8 态无 stale）。
> 它来自操作时的 **409 `PLAN_STALE` 响应**（`Scheduling.tsx:117-123`），
> **必须实现为 mutation 错误分支**，不是状态渲染分支。

### 5.4 OD-6 异步可见（C-7，需后端配合）

| 产物 | 当前 | 目标 | 依赖 |
|------|------|------|------|
| AI 方案解读（30–90s） | `aiNarration === null` 时无法区分「生成中 / 失败 / 未启用」 | 骨架占位 + 进度，超时给重试 | **后端新增 `narrationStatus: 'pending' \| 'done' \| 'failed'`** |
