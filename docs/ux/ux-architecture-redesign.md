# EWOH 用户体验架构重设计（UX-ARCH-2026-09）

> 角色：用户体验架构师
> 日期：2026-09-01
> 范围：`ewoh-spark-app/client` 信息架构与跨页面流程（不改业务语义、不改后端域逻辑）
> 前置成果：本文档建立在 `information-architecture-refactor.md`（UX-IA-2026-08，导航分组已落地）
> 与 `docs/product/UX_DEEPENING_BACKLOG.md`（九态 / 错误五要素 / 离线冲突已闭环）之上，
> 这两项解决的是**页面内**质量问题；本文档解决**页面之间**的流程断裂。

---

## 一、执行摘要

EWOH 的 UX 基础能力已经相当扎实：九态覆盖、错误提示五要素、离线冲突禁止静默覆盖、
无障碍 axe 自动化、性能预算脚本均已落地（见 `UX_DEEPENING_BACKLOG.md` 汇总表）。
用户感知到的"不顺"，**不在单个页面里，而在页面与页面之间**。

本次审计的定量结论：

- **25 个业务页面目录中，23 个的路由出链数为 0**；`client/src/pages/` 全量检索后
  仅 5 个文件含导航调用（Login / MobileWorkbench / Forbidden / CommandMapShell / WorkbenchList）。
- 产品以**页面**为单元组织，而调度业务以**对象**（方案 / 工单 / 设备 / 人员 / 告警）为单元运转。
  这个错配是所有断点的共同根因。

推荐的核心范式转变：**从「页面为中心」转向「对象为中心」**（§五）。

---

## 二、诊断方法

为避免主观判断，全部结论来自可复现的静态检索：

| 步骤 | 方法 | 用途 |
|------|------|------|
| 1 | 对每个 `pages/*` 目录统计 `navigate()` / `<Link to>` 出链数 | 识别页面孤岛 |
| 2 | 全量检索 `useNavigate` / `navigate(` / `window.location` | 排除写法差异造成的误判 |
| 3 | 对比核心流程页面的 API 调用面 | 识别同一对象的重复入口 |
| 4 | 读取跨页引用的数据结构定义 | 识别"不可辨识对象" |

## 三、断点清单（全部附 file:line 证据）

| ID | 断点 | 证据 | 用户可感知后果 |
|----|------|------|----------------|
| **B1** | **页面群岛**：业务页面之间零跳转 | `pages/` 全量检索：25 个页面目录中 23 个出链数为 0；含导航调用的文件仅 `Login.tsx`、`MobileWorkbench.tsx`、`Forbidden.tsx`、`CommandMap/CommandMapShell.tsx`、`RoleWorkbench/WorkbenchList.tsx` | 每完成一步都要回侧边栏重新找页面；已选对象、筛选条件、时间窗全部丢失 |
| **B2** | **审批对象不可辨识**：审批台显示裸 UUID | `ApprovalConsole/approvalConsoleLogic.ts:47-48` — `title: \`调度审批：${s.entityType ?? 'unknown'} ${s.entityId ?? ''}\``、`detail: \`审批实例 ${s.approvalId}\`` | 审批人面对一屏 UUID，无法判断该批什么，必须先去别处查 |
| **B3** | **内容与流程割裂**：同一方案的信息与审批分居两页 | 内容视图 `Scheduling.tsx:394-417`（`approvePlan` → `/api/scheduler/plans/:id/approve`，整方案粒度，信息丰富）；流程视图 `ApprovalConsole.tsx:44-47,85-92`（`listSchedulerPendingApprovals` → `/api/approvals/pending`，按 step 会签粒度，信息贫瘠）；两页无互链 | 想看清方案去 A 页，想走会签去 B 页；两侧是否同步无提示 |
| **B4** | **终态无出口**：下发后流程终止 | `Scheduling.tsx:291-304` — 方案进入 `dispatched`/`executing`/`completed`/`rejected`/`superseded` 后，卡片仅剩一行静态文本（"方案已下发执行"…），无任何通往执行跟踪、决策历史的入口 | 派工是"黑洞动作"：点完不知道活干得怎样 |
| **B5** | **异步负担转嫁用户** | `Scheduling.tsx:376` — `toast.info('调度已排队，请稍后刷新')` | 用户无法区分"慢"与"失败"，只能手动刷 |
| **B6** | **异步产物无 pending 态** | `Scheduling.tsx:184` — `row.aiNarration && (...)`，AI 调度说明异步生成（30–90s），未生成时整块不渲染 | 用户看到永久空白，误判为功能缺失 |
| **B7** | **原始 JSON 暴露给最终用户** | `Scheduling.tsx:195-197` — `<pre>{JSON.stringify(row.metrics, null, 2)}</pre>`，而同卡片 `:177-181` 已有中文格式化指标行（延期/移动/等待/负荷） | 调度员读 JSON dump；与 3.1「统一术语/状态」既有成果直接冲突 |
| **B8** | **审批实例缺对象描述符**（架构根因） | `server/modules/approval/approval.service.ts:54-62` — 创建审批仅持久化自由字符串 `entityType` + `entityId`（`:59`），无枚举约束、无展示字段快照 | 前端**无论怎么写**都无法在审批台显示方案名/指标；这是 B2 不可局部修复的原因 |

### B8 的关键性

B2 不是前端偷懒。`ApprovalInstance` 只存两个自由字符串，审批台**没有反查路径**：
拿到 `entityType='plan'` + `entityId` 后，服务层不知道该去哪张表取标题与指标。
因此 B2 只能通过 §七的「对象描述符契约」从数据层根治。

## 四、根因

```
产品按「系统模块」切页面  →  页面平级、互不相识
        ↓
业务按「对象」流转        →  一个对象的生命周期横跨多个页面
        ↓
页面之间无跳转契约        →  用户被迫充当「页面间的人肉集成层」
```

唯一 counterexample 证明了能力其实存在：`RoleWorkbench/WorkbenchList.tsx:78-90`
（列级 `column.link.to` 下钻）与 `:227`（行级 `resolveRowPath(list, row)` → `navigate(path)`）
已实现**数据驱动的跨页下钻**——只是这套能力从未推广到其他页面。

---

## 五、目标架构：对象中心的三层 UX 架构

### L1 · 对象解析层（Object Spine）

把「页面」降级为对象的**视图**，把「对象」升格为导航**主干**。

- 统一对象路由：`/o/:objectType/:objectId`
- **对象工作台（Object Workbench）**统一骨架：

  | 区域 | 内容 |
  |------|------|
  | 头部 | 对象标识（人类可读标题，非 UUID）+ 状态徽章 + 责任人 + 最后更新 + 数据来源徽章 |
  | 动作区 | **仅**渲染当前状态机允许的动作（复用既有状态机，不新增语义） |
  | 视图区 | 概览 / 关联对象 / 状态历史 / 证据（4 个 tab，URL 同步） |

- 落地基础：直接推广 `WorkbenchList.tsx` 已验证的 `resolveRowPath` 模式，而非新建机制。

### L2 · 旅程层（Journey Rail）

把 20 个平级页面收敛为 **3 条贯穿式旅程**，每条在页面顶部常驻流程带
（当前环节高亮 / 已完成可回看 / 下一步可直达）：

| Journey | 环节 | 覆盖现状 |
|---------|------|----------|
| **J1 排产 → 派工 → 执行 → 收尾** | 生成方案 → 评审会签 → 下发 → 执行跟踪 → 结案复盘 | Scheduling + ApprovalConsole + WorkOrchestration + DecisionHistory |
| **J2 风险 → 处置 → 复核** | 告警发现 → 确认 → 处置 → 关闭/重开 | Alerts + MobileWorkbench + WorkOrchestration/Risks |
| **J3 配置 → 验证 → 发布** | 策略编辑 → 影子评测 → Gate 门禁 → 激活 → 归档 | Simulation + ModelManagement + Operations + Scale |

### L3 · 驾驶舱收敛层

现状「驾驶舱」组含三个数据域不同、用户任务却相同的页面（都是"看当前状态"）：
指挥地图（ALL_ROLES）/ 指挥中心（overview + events）/ 数字世界（空间树 + world state）。

建议收敛为**一个驾驶舱 + 三个视图维度**（空间 / 指标 / 事件），tab 切换 + URL 同步，
直接复用 `Operations` 页已验证的 `?tab=` 直达模式。

> ⚠️ 风险：指挥地图是 ALL_ROLES 唯一入口且模块量较大（4664 行）。
> 收敛**不等于删除**，建议 P2 阶段按使用数据驱动，不在 P0 动它（理由见 §九）。

## 六、设计原则（每条对应已确认断点）

| 原则 | 内容 | 治理断点 |
|------|------|----------|
| **P-1 一个动作，一个出口** | 任何关键动作完成后，必须提供通往下一环节的入口；终态页面提供回溯与关联入口 | B4 |
| **P-2 异步必可见** | 所有异步任务必须有 pending 态与进度；**禁止** "请稍后刷新" 类文案作为终态反馈 | B5, B6 |
| **P-3 跨页引用必用对象描述符** | 页面间传递对象时携带 `{ type, id, title, summary, status, deepLink }`，**禁止**裸 UUID 出现在用户可见位置 | B2, B8 |
| **P-4 状态机单一事实源** | 同一对象的状态跃迁只有一个交互入口；内容与流程在同一对象工作台内合并 | B3 |
| **P-5 不向最终用户暴露原始结构** | JSON dump、内部枚举、审批实例 ID 不得直接呈现；调试信息进"复制诊断信息" | B7 |
| **P-6 页面之间可跳转** | 新建页面必须声明其上下游 Journey 位置与出入链 | B1 |

## 七、关键契约：对象描述符（Object Descriptor）

B2/B8 的唯一根治手段。在审批（及所有跨对象引用）创建时快照展示字段：

```ts
interface ObjectDescriptor {
  objectType: 'scheduling_plan' | 'work_order' | 'device' | 'person' | 'alert';
  objectId: string;
  title: string;              // 人类可读标题，替代裸 UUID
  summary?: string;           // 一句话摘要（如"延期 42min · 负荷 87%"）
  status?: string;            // 快照时的状态
  metrics?: Record<string, number | string>;  // 决策所需关键指标
  requestedBy?: string;
  deepLink: string;           // 前端路由，如 /o/scheduling_plan/<id>
}
```

配套改动（可控）：

1. `approval.service.ts` `createApproval` 增加可选 `subject: ObjectDescriptor`（向后兼容）；
2. `SchedulerPendingApproval` 增加 `subject?` 字段；
3. `approvalConsoleLogic.ts:47-48` 优先渲染 `subject.title` / `subject.summary`，
   缺失时回退到现状文案（灰度安全）；
4. 审批行增加「查看方案」深链按钮 → 直连对象工作台。

> 收益不只在审批台：所有"某处引用了另一个对象"的位置（通知、告警、门禁、证据）
> 都能复用同一契约，一次性消灭系统内所有裸 UUID。

## 九、落地路线（影响 × 收益矩阵）

| 优先级 | 任务 | 影响 | 收益 | 依赖 | 预估改动量 |
|--------|------|------|------|------|-----------|
| **P0-1** | 对象描述符契约（§七 全部 4 步） | 高 | 高 | 后端 1 个接口加可选字段 | 小 |
| **P0-2** | 终态出口补全：下发后「查看执行」+ 终态「查看决策历史」（§八） | 高 | 高 | 无 | 小 |
| **P0-3** | 异步可见：生成中态 + AI 说明 pending 占位（§八） | 中 | 高 | 无 | 小 |
| **P0-4** | 去 JSON dump：指标卡 + 折叠式原始视图 | 中 | 中 | 无 | 小 |
| **P1-1** | 抽取对象工作台骨架（L1），先接 `scheduling_plan` | 高 | 高 | P0-1 | 中 |
| **P1-2** | J1 旅程流程带（Journey Rail）接入排产/审批/执行三页 | 高 | 高 | P1-1 | 中 |
| **P1-3** | 审批入口合并：排产页与审批台共用同一对象工作台 | 高 | 高 | P1-1, P0-1 | 中 |
| **P1-4** | J2 风险旅程（告警 → 处置 → 复核） | 中 | 中 | P1-1 | 中 |
| **P2-1** | J3 治理旅程 | 中 | 中 | P1-1 | 中 |
| **P2-2** | 驾驶舱三页收敛为一个驾驶舱三视图 | 中 | 高 | 使用数据 + 产品拍板 | 大 |

**排序理由**：P0 四项都是**小改动、高感知**，且互不依赖、可立即并行开工，
不需要等 L1 骨架；它们直接消灭用户每天都会撞到的断点。
L1/L2 是结构性改造，放在 P1，且以 P0-1 的契约为前置——有了描述符，
对象工作台才有统一的渲染数据源。

## 十、验收标准（可测，非主观）

| 编号 | 验收项 | 判定方式 |
|------|--------|----------|
| A-1 | 任意两个存在业务先后关系的页面之间，存在不超过 1 次点击的直达入口 | 静态检查：新增断言扫描 `pages/` 出链数，任一 Journey 相邻环节必须 ≥1 条互链 |
| A-2 | 用户可见区域零裸 UUID | E2E：审批台、通知、告警三处断言渲染文本不含 32/36 位十六进制串 |
| A-3 | 零 "请稍后刷新" 类终态文案 | 静态检查：`pages/` 内匹配 `/请.*刷新|稍后重试/` 且非错误态的文案为 0 |
| A-4 | 每个终态对象卡片 ≥1 个后继入口 | E2E：方案 dispatched 后断言存在"查看执行"按钮且可跳转 |
| A-5 | 页面内无 `JSON.stringify` 直接渲染 | ESLint 规则或静态扫描 |
| A-6 | 异步产物 100% 有 pending 态 | 单测：aiNarration 未生成时断言渲染占位而非空白 |

建议沿用既有防回归惯例：单测锁定结构 + E2E 锁定行为（参照 `navigation.ia.test.ts` 做法）。

## 十一、明确不做（避免过度设计）

- **不新增业务语义**：状态机、权限矩阵、调度算法一律不动，本次只改交互组织方式。
- **不在 P0 拆 `/operations`**：上一轮 IA 重构已裁决（tab + ⌘K 直达已解决可达性），
  实体拆分留待使用数据驱动。
- **不在 P0 收敛驾驶舱**：指挥地图是 ALL_ROLES 唯一入口，改动面大，需产品拍板。
- **不重写既有 UX 能力**：九态、错误五要素、离线冲突、无障碍均为已验证资产，复用而非替换。
