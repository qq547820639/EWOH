3. 可数字化验证的事项实际执行：源码调用追踪、数据库约束验证、隔离迁移、模拟输入、故障注入、算法比较和浏览器流程。只有确需真实硬件、现场网络、真实人员或外部资质的事项才列为线下验证。
4. 自主执行不等于调用真实设备、向他人发消息、同步真实云端、覆盖现有数据库或发布生产版本。验证使用可识别的隔离环境；这些外部动作不是本次代码走读的交付内容。
5. 使用中文交付，保留真实英文符号和路径。清楚区分当前源码事实、运行实测、合理推断、历史线索、已证实缺陷、待验证风险与改进建议。

六、重建真实架构与调用链

至少提供运行拓扑图、模块依赖图、关键数据流图、业务时序图和核心实体关系图。图中的每条重要边都关联源码调用、注册、订阅或网络协议证据；推测边用明确标记，未找到连接就报告缺口。

必须追踪下列链路，按当前实现解释串行、并行、独立进程、未连接及环境条件：

1. 用户访问/登录 → Token 验证 → 角色与组织范围 → 请求事务/GUC → RLS 查询 → 响应 → 前端缓存/展示。
2. 设备/环境/视觉/UWB 输入 → 适配归一化 → 本地持久化 → 不同事件流分发 → 推理/世界投影/上行桥 → 平台摄入 → 风险/质量事实。
3. 任务/订单/物料/班次/设备事实 → 世界快照及版本 → 资格/约束/路径 → 求解 → 方案持久化 → 独立身份审批 → 资源预约 → 派工/分波 → 事件与前端刷新。
4. 控制请求 → 审批授权及作用域 → 命令排队 → 投递前复核 → 边缘 ACK → 适配器执行 → 回执/重试/死信 → 平台事实与审计。
5. 人工或设备执行回执 → 身份/设备/计划匹配 → 状态机/CAS → 执行、任务和反馈记录 → 偏差/复盘。人工回执与设备事实入口分别追踪。
6. 运行记忆/反馈 → 学习信号 → 评估/影子验证 → 提案 → 审批/激活 → 实际消费者 → 回滚；核查是否真实影响当前行为。
7. 移动端操作 → 离线保存 → 账号/租户隔离 → 多标签页协调 → 重连提交 → 幂等/冲突 → 服务端事实 → 客户端状态对账。
8. 飞书事件/卡片回调 → 原始请求验签 → 重放/业务幂等 → SQLite 事务 → 状态同步/外部调用 → 重试与恢复。

每条链记录入口、文件:行号、类/函数、请求/事件结构、表/队列、状态变化、异常支路、权限、事务、测试和实测证据。按源码分别解释派工成功、sent、deliveredAt、gateway ACK、执行成功和业务完成，不能合并为一个“成功”。

七、本仓库需要重点核对的边界

以下均是核查题，不是预先认定的缺陷：

- Edge ContractWorldStore 与调度 WorldStateService 的关系；NestJS 世界快照的数据来源；是否存在未连接或语义不同的多套投影。
- Edge 推理与世界投影是否并行订阅不同数据流；帧数窗口是否被文档误写为严格时间窗口。
- 根入口、独立控制代理、各上行桥、CP-SAT worker 是否分别启动；“Python 基础运行时零第三方依赖”是否被错误扩大到整个仓库。
- standalone/legacy 模块注册与注释/日志是否一致；审批实际注入的持久化实现；手动构造服务与私有事务上下文访问是否形成隐藏依赖。
- RLS 非特权角色、SSE/后台任务的组织过滤、嵌套事务/GUC 恢复、独立提交审计、外层回滚后的失败留痕。
- world snapshot、schema-manifest、ORM、迁移、实际表与 OpenAPI 是否一致；不能将部分规划清单当完整数据库目录。
- 事件订阅、线程、队列、定时器、连接池及退出顺序是否有明确上界和关闭协议；数据读取失败是否被空集合掩盖。
- 前端不同 Vite 入口的环境变量与运行行为、Token/Cookie/CORS、离线重试协调和身份切换残留。
- 启动脚本中的云同步、场景重置、数据库清空、默认账号、进程终止等副作用，以及 CI 是否把 SKIP/UNAVAILABLE 算作 PASS。
- 旧 UI、冻结发布副本、模拟器和测试替身的边界；是否存在“文件存在但未接线”“API 成功但没有持久化”“页面有按钮但业务未闭环”。

八、质量问题与改进建议

1. 检查职责过大、重复实现、循环依赖、跨层调用、接口泄漏、动态配置、死代码、类型弱化、宽泛异常吞噬、错误契约、并发竞态、无界缓存/队列、资源泄漏、查询性能和测试替身失真。
2. 安全核查聚焦实际代码：身份/租户隔离、对象级授权、审批独立性、输入验证、文件与出站请求边界、凭据保护、外部执行副作用和审计可信度。不要把理论风险直接标为已存在漏洞。
3. 每个发现包含编号、类别、优先级、确认状态、文件与行号、触发前提、证据/最小复现、影响范围、根因、建议、回归验证和残余风险。合并同一根因，避免重复计数。
4. 文件长只代表需要更多阅读，不自动等于设计缺陷；重构建议要说明具体职责耦合、故障模式、收益、兼容风险和实施成本。
5. 区分立即修复、近期改善、长期演进与证据不足。没有证实的问题可写待验证，不为凑数量制造缺陷。

十二、基于通用工程知识的独立架构判断

这一节要求你在完成当前源码核查后给出明确的架构裁决。通用工程知识只能提供分析框架和待验证假设，不能证明当前仓库存在某个缺陷；当前仓库事实必须绑定文件、行号、运行结果或数据库证据。每条判断写置信度，并说明什么证据会推翻它。

我的当前暂定判断是：**需要边界收敛和局部重构，不需要推倒重写，也不应立即拆成一组微服务**，置信度中等。该判断来自目前已经看到的结构特征：云侧 NestJS/PostgreSQL、边缘 Python/SQLite、React 前端和飞书侧车本身是合理的运行时分层；更值得优先处理的是多套世界状态的权威关系、调度/控制服务的编排边界、边缘消费者生命周期、失败语义和证据链，而不是目录数量或语言数量。如果后续证实当前模块隔离、恢复能力和维护成本已达到目标，应缩小重构范围；若证实单体存在无法通过模块化和容量优化解决的独立扩缩容或故障隔离需求，再重新评估服务拆分。

这是一份负责人立场和待验证路线，不是要求后续审查者赞同的预设答案。鼓励根据源码和实验反驳，包括裁决某部分不需要重构。本节补充的是分析要求，没有授权在本次走读中直接实施下面的业务改造。

建议把目标形态描述成以下五个边界，并逐一用代码证据验证：

1. **云侧控制面**：NestJS + PostgreSQL 对组织权限、调度方案、审批授权、任务状态和学习治理等平台业务事实负责。设备实际执行状态来自受信回执，ERP/MES 等外部系统也可能拥有其业务数据；按事实类型定义唯一写入责任和对账协议，不能把平台数据库等同于全部现实事实。
2. **边缘执行面**：Python 负责设备接入、归一化、质量标记、本地缓冲、推理、适配器和回执；边缘可在断网时安全缓存和降级，但不应悄悄成为云侧调度事实的第二权威。设备控制器保留实时安全控制和本地联锁，平台授权不能覆盖设备拒绝执行的权利。
3. **集成适配面**：飞书侧车负责消息/卡片/同步等外部副作用，用户动作经过主业务授权和状态机后才成为业务变更。先核查已有持久重试机制，只有证实事务提交与外部发送之间存在丢失窗口时，才选择复用或增加 outbox；单纯增加队列不能证明投递可靠。
4. **契约面**：跨端事件、身份、组织、资源、世界快照、状态机和执行回执使用版本化契约；生产消费方、兼容窗口、schema 漂移和生成链必须可追踪。
5. **体验面**：React 页面、SSE、React Query、离线队列和 Service Worker 只负责呈现和可靠交互，服务端权限与业务状态机保持唯一裁决。

至少比较以下三种同一问题的方案，不能把用途不同的项目凑成候选：

| 方案 | 功能匹配度 | License 兼容性 | 维护活跃度 | 安全风险 | 代码质量 | 适配成本 | 当前倾向 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 保留当前运行时，只补测试、边界、生命周期和失败语义 | 已有功能复用度高 | 不新增依赖时没有新增许可证，但现有许可仍需核验 | 当前提交频率、问题处理和依赖支持状态待查 | 有利于集中修复，可能保留既有耦合风险 | 改善局部质量，对跨模块耦合帮助有限 | 预计最低，需确认问题范围 | 作为短期基线 |
| 保留 Python/NestJS/React/侧车，按领域契约做模块化重构和渐进替换 | 已有功能复用度高，可针对已证实耦合 | 沿用与新增依赖分别核验 | 实际维护证据待查；模块化本身不证明活跃 | 可明确权限/事务边界，也有迁移回归风险 | 适合针对性降低依赖和状态耦合，需对照验证 | 预计中等，需按模块测量 | **当前首选** |

这个表是架构方向的初步裁决，不是对外部产品、框架或许可证的实时调研结论。只要后续真的要引入新框架、消息系统、数据库、工作流引擎或求解器，就必须按第九节实际访问官方资料、GitHub、许可证和安全公告后重新比较；在调研完成前不得把表中的成本或维护判断写成已证实事实。

如果由我负责，我会按以下顺序推进，而不是按“文件最长”或“最容易重命名”的顺序：

1. **先建立行为基线和架构不变量**：锁定身份/租户隔离、审批独立性、计划版本、命令授权、执行回执、数据来源、模拟/真实边界和状态终态；复用现有正反例，仅补缺失验证。基线不应固化已证实错误行为，修复时明确记录行为变化。
2. **优先验证并修复可靠性问题**：对边缘 pipeline/projection/上行消费者的取消、join、队列上界和关闭顺序做故障实验；对读取异常返回空集合、安全材料缺省等分支，先核验调用方、部署模式、替代保护及兼容策略。只修复复现或充分证明的问题，保留有明确依据的降级设计，验证重启、断网、重复和乱序行为。
3. **明确世界状态和契约权威**：先对账 Edge 本地投影与平台快照已有的来源、版本、时间和新鲜度字段，补实际缺口。不同用途的投影可并存；只对已证实的冲突写入者或语义重复建立兼容迁移，在消费者迁完且证据可追溯后删除冗余路径。
4. **渐进调整调度/控制编排**：优先保持外部 API 和持久化契约稳定，在已证实的职责耦合处提取领域规则、应用编排、存储和传输接口。纯对象构造可保留手动 new；受框架生命周期、配置和事务管理的依赖使用显式注入，替换私有上下文访问。先选一条纵向业务链试点，只有试点降低修改成本和回归风险后才推广。
5. **按证据处理前端离线和侧车副作用**：核验已存在的身份命名空间、容量限制、幂等、冲突处理和持久重试，不重复建设。只有跨账号残留、重复提交或同步丢失等问题得到证实时，才选择统一上下文、补失效机制或引入可靠投递；保留外部集成与主业务事实的边界。
6. **最后清理和优化**：依据运行数据处理慢查询、重复读取、包体和队列积压，删除已确认无消费者的遗留入口、占位部署和重复文档；保留仍被发布或验证链消费的历史文件并标注边界。

每个阶段必须写出目标、文件范围、前置依赖、兼容策略、数据迁移方案、预期收益、成本/不确定性、验收证据、回滚方式和停止条件。涉及数据库时优先采用扩展—迁移—收缩，证明旧版本仍能兼容新数据；不能无损回滚时提供可演练的备份恢复或前向修复方案。新旧实现对照优先用于纯计算或隔离环境，真实写入和设备命令始终只有一个执行者，不为影子比较重复发送副作用。授权不成立时拒绝平台命令，设备实时安全能力保持独立。成功标准是业务链、故障恢复、权限隔离、延迟/吞吐基线和维护成本改善，而不是文件变短、目录变整齐或新增抽象数量增加。

用重构前后的同一组场景衡量收益：相同业务变更涉及的模块数、跨层依赖数量、失败恢复成功率、重复业务副作用、关键接口 p95/p99、队列峰值和测试反馈时间。先测基线，再设目标，不编造收益百分比或工期。若试点增加耦合、破坏不变量或收益不足以覆盖迁移成本，应停止扩展并修订方案。

重构期间保留这些原则：不按目录机械拆分；不因为服务很长就拆服务；不把“事件驱动”当作解决一致性的答案；不把缓存/投影升级成第二事实源；不让 UI 权限替代后端授权；不在没有迁移、兼容和回滚证据时切换生产路径。
