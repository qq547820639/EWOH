# 开发指令：AI 生成调度方案自然语言说明（NL 说明层）

- 版本：v1.0
- 日期：2026-08-21
- 状态：待评审 / 待实现
- 关联：排产调度（Scheduling）、AI 模块（ai.service / ark.service）、调度求解器（heuristic / cp-sat）

---

## 0. 执行摘要

当前排产调度方案对用户展示的是求解器原始产出（assignments + metrics + 状态流转），
数字多、业务解释弱（且 metrics 全 0 的缺陷已于 2026-08-21 修复——根因 person 状态
大小写不匹配，见 commit 073e95b）。本指令要求：**在方案生成链路中新增"AI 说明层"**——
求解器负责产生原始调度数据（职责不变），AI（LLM，经既有 Ark 通道）负责把原始结果
转换为用户可读的**自然语言调度说明**，随方案一并落库、随方案详情/审批页展示。

目标：让班组长/调度员看到方案时，第一眼读到的不是数字矩阵，而是"为什么这么排、
排了什么、有什么风险、怎么调整"的通俗说明。

---

## 1. 职责边界（必须严格划分）

| 职责方 | 负责 | 不负责 |
|---|---|---|
| 调度求解器（heuristic / CP-SAT + 统一评估器）| 生成 assignments、metrics、scoreBreakdown、decisionTrace、baselineDelta | 不得生成任何面向用户的自然语言文案（保持确定性、可复现） |
| AI 说明层（新服务 SchedulingNarratorService）| 消费求解器原始输出，生成自然语言调度说明 | 不得修改/伪造 assignments 与 metrics；不得参与求解决策 |
| 前端（排产调度详情/审批）| 展示 AI 说明（LLM 生成文本）+ 保留原始数据可展开查看 | 不得在前端本地拼装"伪说明" |

**硬性约束（不得违反）**：
- AI 说明层是**纯后置/纯只读**：只读 plan 快照（assignments/metrics/decisionTrace），
  任何情况下不得回写求解结果。
- 求解器代码**禁止**引入 LLM 调用（当前 heuristic-scheduling-solver 明确无 LLM，保持）。
- AI 说明**不得替代**审批所需的结构化事实（冲突列表、硬约束违反项、metrics）——
  说明是"解释层"，事实层仍是结构化的。

---

## 2. 数据流转（求解器输出 → AI 输入）

### 2.1 数据源（求解器/评估器输出，均为现有字段）

构造 AI 输入的数据取自 ewoh_schedule_plan 及其关联，**不得新增求解字段**：

| 输入块 | 来源 | 字段 |
|---|---|---|
| 方案概要 | ewoh_schedule_plan | plan_id、version、status、trigger_type、strategy、created_at |
| 指标 | metrics_json | changeCost、lateMinutes、maxWorkload、walkingMeters、stationWaitMinutes（及后续扩展） |
| 任务分配 | ewoh_scheduling_plan_assignment | task_id、person_id、device_id、station_id、planned_start、planned_end、route_id、status |
| 冲突/拒绝 | ewoh_scheduling_conflict + decisionTrace（assignment.explanation_json）| 冲突类型、涉及任务/资源、原因（如 person_unavailable、time_conflict、hard_violation）|
| 基线对比 | plan 对比服务（plan-compare）| 本次方案 vs 上一版/基线的指标差（改善/恶化项）|

### 2.2 流转时序（需按此实现）

```
[求解] solver.solve() 产出 assignments + metrics（现状不动）
   │
   ▼
[评估] objective-evaluator 计算 metrics/scoreBreakdown/baselineDelta（现状不动）
   │
   ▼
[落库] plan.service 持久化 plan + assignments（现状不动）
   │
   ▼
[新] AI 说明层：构建 LLM 输入（结构化压缩后的 plan 快照）→ ArkService.ask
   │         → 生成 narration 文本 → 幂等落库（ewoh_schedule_plan.ai_narration 或
   │           plan 扩展表 ewoh_schedule_plan_narration）
   ▼
[展示] 前端方案详情/审批页渲染 narration；原始数据可折叠展开
```

- 生成时机：方案**首次落库后异步执行**（不得阻塞 createRun 响应；失败不阻断方案生成）。
- 幂等：同一 plan_id 仅生成一次（落库前查重；失败重试可覆盖，成功即锁）。
- 超时与降级：LLM 调用设超时（如 15s，对齐平台 P99 <10s 之外的异步路径）；LLM 不可用/
  超时/输出不合格 → 回退**规则模板说明**（见 §4.3），并标记 narration_source=rule_fallback。

## 3. 输出要求（AI 生成文本约束）

### 3.1 必须满足
1. **自然、通俗**：面向班组长/调度员，避免术语堆砌；数字保留但用业务语言包装
   （例："高负荷人员从 3 人降至 1 人"而非 "maxWorkload 0.6→0.4"）。
2. **符合业务语境**：使用"人员/设备/工位/外骨骼/转运/装配"等业务词；人员用姓名、
   设备用编号（EXO-101）、工位用名称。
3. **结构清晰**：建议固定四段式——
   ① 一句话结论（方案要点）② 主要调整（相比基线/上一版，排/改/停了什么）
   ③ 风险与关注点（未满足项、高负荷/低电量/路线风险）④ 建议动作（可选）。
4. **事实锚定**：文本中出现的每个数字/结论必须能在输入数据中溯源（AI 需引用
   具体任务/指标）；不得编造输入中不存在的任务或指标。
5. **长度适中**：中文 200~400 字；可直接用于审批页展示。

### 3.2 必须禁止
- 不得输出 markdown 代码块、表格语法、JSON（与既有 AiService 提示词约束一致）。
- 不得输出"作为 AI，我无法……"类免责话术。
- 不得虚构原因（如输入无冲突时不得编造"存在时间冲突"）。
- 不得包含求解器未产出的人名/设备号。

## 4. 具体实现建议

### 4.1 新增服务与落点

- 新建 `server/modules/scheduler/narration/scheduling-narrator.service.ts`
  （或复用 `server/modules/ai/` 扩展 `AiService`——建议独立服务，依赖
  `ArkService`（@Optional）+ `ObjectiveEvaluator` 产物，保持 scheduler 域内聚）。
- 依赖注入：`ArkService`（既有，ai.module 导出）、`PlanRepository`（既有）。
- 表：`ewoh_schedule_plan` 增加 `ai_narration text null` + `narration_source varchar null`
  （'llm' | 'rule_fallback'）——需 migration + rollback + verify + runner 注册（7 处，
  参照 standalone_022 同构约定）。

### 4.2 LLM 调用契约（复用 ArkService）

```ts
// 示意（非最终代码）：构造结构化输入 → ark.ask
const userPrompt = buildNarrationPrompt(planSummary, assignments, conflicts, baselineDelta);
const result = await this.ark.ask(
  SYSTEM_PROMPT, // 见 §4.4 示例
  userPrompt,
  { temperature: 0.3, maxTokens: 800, timeoutMs: 15_000 },
);
const narration = sanitizeNarration(result.text); // 去 markdown 围栏、去空行、截断 800 字
```

- `ArkService.ask` 既有签名（systemPrompt, userPrompt, opts）直接复用；
  未注入 ArkService（未配置）时直接走规则回退。
- 并发：方案可能一次生成 3 份（A/B/C 影子方案）——需串行或限流（如 Promise.allSettled
  并行但全失败容忍）；生成失败**不得**导致方案状态变化。

### 4.3 规则回退模板（LLM 不可用时的保底说明）

按 metrics/assignments 确定性拼装，例：
"本方案共分配 N 个任务（共 M 个任务，K 个暂未排入）。较上一版：
高负荷人员减少 X 人、低电量风险设备 Y 台已避开、预计新增步行 Z 米。
需关注：任务 T1 因人员技能不匹配未排入；工位 S3 容量已满。"
回退说明同样要求事实锚定（直接取自数据），仅语言模板化。

### 4.4 System Prompt 示例（需按业务调优后固化）

```
你是工厂生产调度系统的方案解读助手。你只负责把求解器给出的调度方案
翻译成班组长/调度员能直接读懂的中文说明，不参与任何决策。
输入是一份结构化的调度方案数据（任务分配、指标、冲突、与基线的对比）。
输出要求：
1. 四段式：一句话结论 / 主要调整 / 风险与关注点 / 建议动作；
2. 用业务语言（人员用姓名、设备用编号、工位用名称），数字用"从 X 降至 Y"式表达；
3. 只描述输入中真实存在的事实，禁止编造任务、指标或原因；
4. 中文 200-400 字；不得输出 markdown、代码块、JSON、表格；
5. 没有风险时如实写"未发现明显风险"，不要硬凑。
```

### 4.5 前端展示

- 排产调度方案详情/审批页：方案头部展示 AI 说明卡片（narration_source=llm 显示
  "AI 解读"徽标；rule_fallback 显示"规则摘要"），下方保留"原始数据"可折叠区
  （assignments 表 / metrics 数字）。
- 审批弹窗（工作台/审批控制台）可引用该说明作为审批人第一屏信息。

## 5. 验收标准（实现完成后逐条核对）

1. 触发 MANUAL 调度生成方案后，ewoh_schedule_plan.ai_narration 在异步窗口内
   （≤30s）出现非空中文说明，narration_source='llm'。
2. 说明文本满足 §3.1 全部要求（可用人工抽检 + 脚本断言：无 markdown 围栏、
   长度 200-400、含"任务/人员/风险"关键业务词）。
3. 说明中每个任务/设备/工位引用均能在该 plan 的 assignments 中找到（自动核对）。
4. 停用 Ark（模拟不可用）时生成方案 → narration_source='rule_fallback'，模板说明
   可用且不报错；createRun 响应时间不受 LLM 影响（异步）。
5. 同一 plan_id 重复生成任务不产生重复 narration（幂等校验通过）。
6. 求解器代码无新增 LLM 调用；metrics/assignments 与未加说明层时完全一致
   （回归：对同一输入两次求解结果逐位一致）。
7. migration 可 apply/rollback/verify（runner 7 处注册完整）。

## 6. 里程碑拆分（建议实施顺序）

- M1（P0）：表结构 migration + SchedulingNarratorService 骨架 + 规则回退模板 + 落库幂等。
- M2（P0）：Ark 接入（system prompt 固化）+ 异步生成接线（createRun 后触发）+ 前端展示。
- M3（P1）：prompt 质量迭代（对照真实方案人工评审 10 份）、metrics 扩展时 prompt 同步。
