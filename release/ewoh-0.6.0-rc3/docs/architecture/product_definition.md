# 工厂具身智能操作系统（Embodied Factory OS）产品定义

> 文档状态：V0.6 基线产品定义（已按 2026-07-31 评审结论修正 4 处草稿缺陷，详见文末“修订记录”）
> 配套文档：`docs/architecture/embodied_factory.md`（架构规范）、`docs/acceptance/embodied_factory_acceptance.md`（验收指标）

## 一、产品定义

项目不再仅定位为“外骨骼人员作业协同与风险分析平台”，而升级为：

**工厂具身智能操作系统（Embodied Factory OS）**

其核心任务是建立一套统一的工厂时空世界模型，将以下对象纳入同一套感知、推理、仿真和决策体系：

- 人员；
- 外骨骼；
- 工位与产线；
- 生产设备；
- 物料与任务；
- 摄像头、UWB 及环境传感器；
- 人体动作、负荷、风险和疲劳趋势；
- 生产节拍、拥堵、异常和调度方案。

现有 EWOH 仓库已经具备设备接入、遥测采集、本地推理、事件、任务、API、部署与验收骨架；当前活跃代码位于 `src/edge_platform/`，部署采用设备控制区、采集适配区、平台服务区和用户接入区的四区结构。新阶段应在保留这些能力的基础上，增加空间孪生、感知融合、世界模型、调度仿真和指挥地图。

首期不追求全工厂高写实三维，也不追求无人化自动调度，而是完成五个闭环：

1. **看得见**：平台能够在地图上看到人员、外骨骼、设备、工位、任务和风险。
2. **看得懂**：系统能够理解人员正在做什么、身体负荷如何、现场是否异常。
3. **能预测**：系统能够预测短期疲劳、任务延误、设备失联、电量不足和空间拥堵。
4. **能建议**：系统能够给出人员调度、任务调整和休息安排建议，并解释原因。
5. **能学习**：实际执行结果能够回流，持续校准规则、模型和调度参数。

## 二、实施原则

### 2.1 先二维半，再局部三维

第一阶段以二维或 2.5D 指挥地图为主。

工厂管理最需要的是准确的位置、状态、关系和趋势，而不是写实画面。完整三维重建只用于：

- 复杂工位；
- 高风险区域；
- 培训与事故复盘；
- 需要空间遮挡、姿态或轨迹分析的场景。

### 2.2 静态空间与动态实体分离

工厂空间底图低频更新，人员和设备状态高频更新。

静态层包括：

- 厂房结构；
- 产线；
- 设备外形；
- 工位；
- 通道；
- 禁区；
- 摄像头视锥；
- UWB 基站覆盖区。

动态层包括：

- 人员位置与骨架；
- 外骨骼状态；
- AGV、叉车和物料；
- 当前任务；
- 告警；
- 风险热力图；
- 预测轨迹。

这样可以避免每秒重新构建三维场景。

### 2.3 多传感器融合，不依赖单一摄像头

人员空间状态应由多种数据共同确定：

```
人员状态 = UWB位置 + 外骨骼IMU姿态 + 视觉骨架 + 工位语义 + 任务上下文
```

摄像头负责理解“看见了什么”，外骨骼负责提供身体运动和负荷信息，UWB 负责提供稳定位置，工单系统负责解释人员为什么出现在该位置。

### 2.4 人在回路

在试点和早期生产阶段：

- 调度系统只能提出建议；
- 班组长或授权人员确认后执行；
- 高风险建议必须附带理由；
- 系统不得根据单次算法结果直接处罚员工；
- 员工应能申诉、标记误判或说明特殊情况。

### 2.5 安全控制不进入平台

EWOH 平台继续保持监督、分析和建议定位。急停、限扭、关节实时控制、助力闭环、限速和失联安全态必须保留在外骨骼设备控制器本地，平台不得绕过。

## 三、技术架构

建议将平台拆成九层。

### 3.1 设备与现场层

包括：

- 外骨骼控制器；
- IMU、编码器、力矩和压力传感器；
- 电池、故障码和设备健康信息；
- UWB 标签与基站；
- 固定摄像头、深度摄像头；
- 环境温度、振动、噪声和空气质量传感器；
- PLC、MES、WMS、AGV、设备状态接口。

### 3.2 边缘适配层

负责：

- 设备协议解析；
- 数据源身份认证；
- 时间戳统一；
- 采样率治理；
- 缓存补传；
- 心跳；
- 数据质量评分；
- 协议版本管理；
- `real`、`controlled_test`、`simulated` 来源隔离。

现有统一适配层契约可以继续保留，但需增加摄像头、UWB、MES 和空间坐标适配器。仓库现有协议规范已经覆盖身份、心跳、电量、故障、遥测、缓存补传和安全状态，可作为扩展基础。

### 3.3 流处理层

试点阶段建议采用较轻的消息架构：

- Redis Streams 或 NATS 负责实时事件；
- PostgreSQL 负责业务数据；
- 时序扩展或独立时序数据库负责高频遥测；
- 对象存储负责图片、视频证据、点云和三维资产；
- WebSocket 负责前端实时推送。

数据流分成四类：

1. 高频遥测流；
2. 设备与人员状态流；
3. 业务事件流；
4. 视频和三维资产索引流。

> 实现说明：当前 V0.6 以标准库实现的进程内可插拔消息总线（`src/edge_platform/edge/bus.py`）作为参考实现，对外提供与 Redis Streams/NATS 同构的接口契约；生产环境可在同一接口下注入 Redis Streams/NATS/PostgreSQL/时序库，上层无感知。前端推送当前为 1 秒 HTTP 轮询，计划在 V0.8 引入 SSE，规模化后切换至 WebSocket（见验收文档）。

### 3.4 空间数字底座

建立统一空间坐标体系：

```
集团
└── 工厂
    └── 车间
        └── 产线
            └── 区域
                └── 工位
                    └── 设备/人员/任务
```

每个实体应具备：

- 唯一 ID；
- 父级空间；
- 坐标；
- 朝向；
- 边界框；
- 状态；
- 数据来源；
- 置信度；
- 更新时间；
- 版本。

空间资产建议统一输出为：

- GeoJSON：二维区域和路线；
- GLB/glTF：轻量三维模型；
- 3D Tiles：大规模场景分块；
- 点云或 Gaussian Splat：局部高写实场景；
- JSON 拓扑：工位、路线和邻接关系。

### 3.5 感知融合层

输入：

- UWB 坐标；
- 外骨骼 IMU；
- 视觉检测与骨架；
- 设备状态；
- 工位占用；
- MES 任务；
- 环境信息。

输出：

- 人员统一位置；
- 人体姿态；
- 当前动作；
- 工位占用；
- 人员—设备—任务绑定关系；
- 数据质量和置信度；
- 异常冲突。

融合规则应优先可解释。例如：

- UWB 显示人员在 A 工位，视觉也在 A 工位：高置信；
- UWB 显示 A 工位、视觉显示 B 工位：产生传感器冲突事件；
- 摄像头被遮挡，但外骨骼 IMU 和工位签到正常：继续推断，但降低置信度。

### 3.6 工厂世界模型层

世界模型不是一个单独的大模型，而是一个持续更新的状态系统。

它维护：

- 当前状态；
- 历史状态；
- 实体之间的关系；
- 事件因果链；
- 短期预测；
- 模型不确定性。

推荐使用事件驱动结构：

```
员工进入区域
→ 与外骨骼完成绑定
→ 领取任务
→ 到达工位
→ 开始搬运动作
→ 累计负荷上升
→ 外骨骼电量下降
→ 工位出现积压
→ 系统生成调度建议
→ 班组长确认
→ 任务重新分配
→ 结果回流
```

### 3.7 决策与调度层

调度器同时考虑：

- 人员技能；
- 任务优先级；
- 工位资质；
- 人员位置；
- 行走距离；
- 当前和累计身体负荷；
- 疲劳趋势；
- 外骨骼电量和健康；
- 生产节拍；
- 设备状态；
- 物料是否到位；
- 安全区域限制；
- 人员偏好和禁忌；
- 班组规则。

调度目标采用多目标优化：

```
J = w_1·产量 + w_2·准时率 - w_3·安全风险 - w_4·人体负荷 - w_5·移动距离 - w_6·换岗成本
```

权重不得由算法自行隐藏决定，应允许工厂配置，并记录每次调整。

### 3.8 场景仿真层

调度前至少生成三个方案：

- 保持现状；
- 最小调整；
- 产能优先；
- 安全与负荷均衡优先；
- 设备异常应急方案。

每个方案展示：

- 预计产量；
- 延误风险；
- 人员负荷变化；
- 行走距离；
- 外骨骼电量消耗；
- 拥堵变化；
- 受影响人员；
- 关键假设；
- 置信度。

### 3.9 指挥地图与本地助手

界面采用类似复杂策略游戏的“上帝视角”，但避免游戏化排名和对员工的过度监控。

核心页面包括：

1. 全厂态势地图；
2. 车间或产线地图；
3. 人员与外骨骼详情；
4. 工位详情；
5. 事件中心；
6. 调度方案比较；
7. 时间轴回放；
8. 数据质量中心；
9. 模型与规则管理；
10. 本地自然语言助手。

## 四、3D 场景建设方案

### 4.1 现场资产盘点

首先收集：

- CAD 图纸；
- BIM 文件；
- 厂房平面图；
- 设备布局图；
- 摄像头安装图；
- UWB 基站位置；
- 消防和安全区域图；
- 工位编号；
- 物流路线；
- 设备尺寸；
- 现有视频监控协议和访问权限。

如果 CAD 资料完整，优先由 CAD 生成空间底图；资料不完整时再进行现场扫描。

### 4.2 三维建模分级

**L0：二维地图**

显示工位、设备、人员位置、路线和区域状态。

**L1：2.5D 地图**

增加楼层、设备高度、摄像头视锥和简单三维模型。

**L2：轻量三维模型**

通过 CAD 或扫描建立可交互的 GLB 模型，用于日常调度。

**L3：高写实局部场景**

仅在重点工位使用点云、摄影测量或 Gaussian Splat，用于事故复盘、培训和复杂空间分析。

### 4.3 摄像头接入步骤

1. 建立摄像头资产台账。
2. 确认视频协议、分辨率、帧率和可访问范围。
3. 完成内参标定。
4. 将摄像头位置和朝向标定到工厂坐标系。
5. 对有重叠视野的摄像头做跨镜跟踪。
6. 增加遮挡、逆光、夜间和反光测试。
7. 默认在边缘侧完成人体检测和骨架提取。
8. 中心平台优先保存结构化结果，不默认长期保存完整视频。
9. 只有事件发生时保存授权范围内的短视频证据。
10. 每个识别结果必须附带置信度、摄像头 ID 和模型版本。

### 4.4 三维验收指标

试点目标建议设为：

- 空间底图关键工位误差不超过 10 厘米；
- 人员区域识别准确率不低于 98%；
- UWB 与视觉融合后，人员定位中位误差不超过 0.5 米；
- 动态状态更新时间不超过 2 秒；
- 摄像头遮挡时能够自动降级到 UWB 与外骨骼数据；
- 场景加载时间不超过 5 秒；
- 普通办公终端保持流畅交互；
- 所有地图实体能够追溯到原始数据来源。

## 五、外骨骼数据接入计划

### 5.1 数据分级

**设备级数据**

- 设备 ID；
- 硬件和固件版本；
- 电量；
- 温度；
- 故障码；
- 通信质量；
- 在线状态；
- 传感器健康。

**运动级数据**

- 加速度；
- 角速度；
- 姿态角；
- 关节角；
- 步态周期；
- 动作频率；
- 身体倾角。

**负荷级数据**

- 助力水平；
- 助力输出；
- 力矩；
- 压力；
- 搬运次数；
- 高负荷持续时间；
- 累计负荷指标。

**业务级数据**

- 绑定人员；
- 当前任务；
- 工位；
- 开始和结束时间；
- 任务进度；
- 异常说明。

### 5.2 接入协议

每个设备厂商必须提交：

- 协议确认书；
- 字段字典；
- 采样率；
- 单位；
- 精度；
- 异常值；
- 丢包策略；
- 缓存容量；
- 时钟同步方式；
- 固件兼容策略；
- 允许命令白名单；
- 禁止写入列表。

所有原始字段进入平台前必须转换为统一语义。

例如：

```json
{
  "entity_id": "EXO-001",
  "worker_id": "W-017",
  "event_time": "2026-07-30T13:15:22.125+08:00",
  "source_type": "real",
  "pose": {
    "trunk_pitch_deg": 28.4,
    "angular_velocity_dps": 16.2
  },
  "load": {
    "assist_level": 0.35,
    "cumulative_load_score": 0.71
  },
  "device": {
    "battery_pct": 42,
    "health": "normal"
  },
  "quality": {
    "packet_loss_pct": 0.3,
    "confidence": 0.96
  }
}
```

### 5.3 数据采集批次

现有仓库建议首批采集站立、行走、弯腰、搬起、放下、搬运和异常姿态数据，并按人员划分训练、验证和测试集，同时要求时间戳、采样率、通道完整性和元数据达到质量门槛。新计划可以沿用该基线，并增加真实工序和多传感器同步数据。

**批次 A：受控动作**

12—20 人，在安全环境中采集标准动作、不同重量、不同台面高度和不同助力等级。

**批次 B：模拟工序**

在不影响生产的区域复现完整工序，采集任务、动作、负荷和视觉同步数据。

**批次 C：真实生产**

取得授权后在真实班次中采集，重点覆盖动作过渡、遮挡、设备差异和个体差异。

### 5.4 标签体系

主标签：

- stand；
- walk；
- bend；
- lift；
- lower；
- carry；
- reach；
- push；
- pull；
- kneel；
- idle；
- unknown。

辅助标签：

- 负载等级；
- 弯腰深度；
- 单手或双手；
- 有无外骨骼助力；
- 工位；
- 任务；
- 是否符合标准作业；
- 是否存在潜在风险；
- 标注置信度。

## 六、算法实施计划

### 6.1 第一阶段：规则与统计模型

不要一开始直接依赖大模型。

优先实现：

- 姿态阈值；
- 高负荷持续时间；
- 动作次数；
- 电量预测；
- 失联检测；
- 工位停留；
- 任务超时；
- 人员进入禁区；
- 传感器冲突；
- 累计负荷积分。

优点是可解释、易验收、便于获得现场信任。

### 6.2 第二阶段：动作识别模型

输入外骨骼 IMU 窗口和视觉骨架，输出动作类别。

实施要求：

- 按人员划分测试集；
- 不允许同一人员的数据同时出现在训练和测试中；
- 每个模型必须有模型卡；
- 保存数据版本、特征版本、模型版本和阈值版本；
- 未知动作必须能够输出 `unknown`，不得强制分类。

### 6.3 第三阶段：负荷与疲劳趋势

首期只做“趋势评分”，不做医学诊断。

可建立：

- 短期动作负荷；
- 班次累计负荷；
- 静态姿态持续时间；
- 高风险动作累计次数；
- 助力收益估算；
- 恢复时间建议；
- 个体基线偏差。

输出形式：

```
当前负荷：中
30分钟趋势：上升
主要原因：连续弯腰时间增加、搬运次数高于个人基线
建议：当前任务结束后安排低负荷工位或短时恢复
```

### 6.4 第四阶段：调度优化

先采用约束优化和启发式算法，再考虑强化学习。

原因是试点期数据有限，强化学习难以保证安全性和可解释性。

首期调度器应具备：

- 硬约束过滤；
- 候选人员生成；
- 多目标评分；
- 方案模拟；
- 理由生成；
- 人工确认；
- 执行结果回流。

硬约束包括：

- 技能和资质；
- 工位授权；
- 健康禁忌；
- 禁区；
- 班次和休息规则；
- 外骨骼型号兼容；
- 设备故障；
- 安全规则。

### 6.5 本地大模型的正确角色

本地大模型不直接负责实时控制，也不直接取代调度优化器。

它主要承担：

- 自然语言查询；
- 事件总结；
- 调度方案解释；
- 规则检索；
- 历史案例检索；
- 交接班摘要；
- 异常根因假设；
- 报告生成。

调度结果必须来自结构化算法，大模型负责解释，不得虚构传感器数据或调度结果。

## 八、数据治理与隐私

### 8.1 数据最小化

默认不采集：

- 身份证等强身份信息；
- 无明确用途的长期精确轨迹；
- 持续保存的原始视频；
- 非必要的生理数据；
- 与安全和生产无关的个人信息。

现有 EWOH 安全策略已经采用匿名编号、最小必要、视频和生理数据需单独授权、高频遥测按窗口保留的原则，应继续作为强制基线。

建议默认采用：

- 边缘推理；
- 中心只保存骨架和事件；
- 原始视频短缓存；
- 无事件自动覆盖；
- 事件证据按权限调取；
- 人脸默认模糊或不识别；
- 非必要不做跨天身份追踪。

### 8.2 数据权利

员工应能够：

- 知道采集哪些数据；
- 知道数据用途；
- 查看与自身有关的主要结论；
- 对错误数据提出更正；
- 对误判进行说明；
- 查询谁访问过敏感数据；
- 在政策允许范围内撤回授权。

### 8.3 数据保留

建议：

- 高频原始遥测：7—30 天；
- 分钟级聚合数据：6—12 个月；
- 事件证据：按事件闭环周期；
- 调度与任务记录：按生产审计周期；
- 审计日志：不少于 180 天；
- 三维底图：按版本长期保存；
- 模型训练数据：单独授权和版本管理。

### 8.4 数据权利（补充）

员工应能够：

- 知道采集哪些数据；
- 知道数据用途；
- 查看与自身有关的主要结论；
- 对错误数据提出更正；
- 对误判进行说明；

## 十三、验收指标

在继承现有 EWOH 启动、API、采集、事件、权限、审计、离线运行和安全边界指标的基础上，增加以下指标。现有仓库已提出 API 读请求 P95 不超过 300 毫秒、遥测端到端不超过 500 毫秒、事件召回率不低于 95%、误报率不高于 5%、来源标识全覆盖以及离线运行等试点门槛。

### 时延与状态

- 状态端到端更新不超过 2 秒；
- 关键风险事件不超过 2 秒到达页面；
- 调度候选返回不超过 5 秒；
- 单班次回放加载不超过 10 秒。

### 数据质量

- 关键通道缺失率低于 1%；
- 设备来源标识准确率 100%；
- 时间同步误差满足各传感器融合要求；
- 关键实体 ID 匹配准确率不低于 99%。

### 空间与视觉

- 重点工位地图误差不超过 10 厘米；
- 人员区域识别准确率不低于 98%；
- 融合定位中位误差不超过 0.5 米；
- 摄像头不可用时能够自动降级。

### 算法

- 核心动作宏平均 F1 不低于 0.85；
- 高风险事件召回率不低于 95%；
- 误报率不高于 5%；
- 所有建议具有分项理由；
- 模型结果 100% 可追溯到模型和数据版本。

### 调度

- 技能、安全等硬约束违规为 0；
- 建议采纳率达到 30% 以上；
- 被采纳建议中，生产或负荷指标至少一项得到改善；
- 人工可在任何阶段否决；
- 未经授权自动调度为 0。

### 安全与隐私

- 平台下发实时关节或安全控制指令为 0；
- 越权访问拦截率 100%；
- 写操作审计覆盖率 100%；
- 未授权视频或生理数据采集为 0；
- 备份恢复成功率 100%。

## 十四、主要风险及应对

### 风险 1：摄像头无法稳定重建完整三维

应对：

- 不将三维重建作为首期必要条件；
- 优先 CAD 和 2.5D；
- 重点工位使用深度摄像头或多摄像头；
- 使用 UWB 和外骨骼补充。

### 风险 2：不同外骨骼协议差异大

应对：

- 建立厂商适配器；
- 定义统一语义模型；
- 要求协议确认书；
- 建立真机契约测试；
- 不直接将厂商字段泄漏到上层业务。

### 风险 3：员工认为系统用于监控或考核

应对：

- 明确安全与能力增强目的；
- 默认匿名编号；
- 不做个人排名；
- 不以单次算法结果处罚；
- 引入员工代表参与规则制定；
- 提供误判申诉。

### 风险 4：疲劳算法被误解为医学判断

应对：

- 只输出负荷和趋势；
- 明确不是医疗诊断；
- 不用“患病”“健康异常”等表述；
- 由人因专家审核指标。

### 风险 5：调度建议影响生产

应对：

- 先影子运行；
- 只记录不执行；
- 与班组长方案对比；
- 达标后进入建议模式；
- 最后才允许有限自动化，且不涉及设备安全控制。

### 风险 6：数据质量不足导致错误推理

应对：

- 所有结果带置信度；
- 低置信度不生成强建议；
- 建立传感器冲突事件；
- 数据质量成为独立地图模式；
- 支持人工标记“现场事实”。

### 风险 7：项目范围失控

应对：

首期只选择：

- 1 个工厂；
- 1 条产线或 1 个车间；
- 3—5 个关键工位；
- 20—50 人；
- 10—30 套外骨骼；
- 1 种主要工序；
- 1 类核心调度问题。

- 数据质量；
- 2.5D 地图；
- 事件回放；
- 安全和隐私；
- 调度影子运行。

可以后置：

- 全厂高写实三维；
- 大规模视频保存；
- 复杂大模型；
- 强化学习调度；
- 多工厂部署。

## 十七、最终产品边界

项目成功不等于建立一个漂亮的三维展示系统，也不等于部署一个能够聊天的大模型。

真正的核心资产是：

1. 人、外骨骼、任务、设备和空间的统一实体模型；
2. 多传感器统一时间和空间坐标；
3. 可追溯的真实生产数据；
4. 人体动作和负荷的长期数据资产；
5. 可解释的风险和调度模型；
6. 可回放、可仿真、可审计的工厂世界模型；
7. 不侵犯设备安全边界和员工基本权利的治理体系。

最终形成的系统应当符合以下定义：

> 工厂以传感器为皮肤，以生产设备为器官，以人员和外骨骼为肢体，以设备本地安全控制为脊髓，以统一时空世界模型为记忆，以调度和仿真系统为大脑，在真实生产过程中持续感知、推理、行动、复盘和进化。
