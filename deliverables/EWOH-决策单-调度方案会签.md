# 决策单：调度方案是否接入 approvals 会签系统

> 提出：产品 ｜ 日期：2026-09-01 ｜ 状态：**待拍板**
> 触发：PRD《对象工作台》工程评估发现（E-3 / Q-7）
> 关联：`docs/product/PRD-object-workbench.md` v1.1 §10 Q-7、
> `docs/product/PRD-object-workbench-dev-feasibility.md` E-3
> **本决策不阻塞对象工作台 PRD 开工**（理由见 §5）

---

## 1. 背景

工程评估发现一个与 PRD 假设不符的事实：**调度方案不进 approvals 会签系统**。

| 项 | 实际情况 | 证据 |
|----|---------|------|
| 调度方案审批 | 走 `/api/scheduler/plans/:id/approve`，**整方案单人批准，无会签** | `Scheduling.tsx:394-417` |
| approvals 系统承载 | 仅 `task` / `dangerous_action` / `control_request` 三类（白名单 fail-closed） | `APPROVAL_ROLE_POLICY:38-46`、`:173-178` |
| 实际创建方 | HTTP `POST /api/approvals` + `control.service.ts`（`control_request` 高危控制指令） | `createApproval(` 全仓调用点 |

由此引出一个**超出原 PRD 范围、但值得单独决策**的治理问题。

---

## 2. 核心问题：审批独立性缺失（待核实）

现状代码路径（`Scheduling.tsx:396-401`）：

```ts
approvePlan(plan.planId, {
  version: plan.version,
  snapshotVersion: plan.snapshotVersion,
  operator: getCurrentOperator(),   // ← 当前登录用户
  reason,
});
```

- 方案由调度员在 `/scheduling` 页生成（"生成方案"按钮，`:372-392`）
- 同一页面的"审批通过"按钮使用 `getCurrentOperator()` 作为审批人
- 页面角色门槛（dispatcher / workshop_lead，`lib/navigation.ts`）意味着
  **生成者与批准者很可能是同一人**

→ 这构成典型的**审批独立性缺失**：自己生成、自己批准。

### ⚠️ 需要工程核实的一点

approvals 系统内部有"发起人回避"设计（`approval-persistence.service.ts:210-211`
记录 `createdBy` 用于「cancel/发起人回避的 initiator 校验」）。
但**该校验是否存在于调度方案的 `approvePlan` 路径，本次未核实**。

| 核实项 | 若为真的影响 |
|--------|------------|
| `approvePlan` 是否校验「审批人 ≠ 方案生成人」 | 若有校验 → 问题不存在，本决策单降级为信息存档；若无 → 治理风险成立 |

### ✅ 核实结论（2026-09-01，已回填 D-3）：**审批独立性缺失属实，且为结构性缺失**

1. **`approvePlanV2` 无发起人回避校验**：`scheduler.service.ts:307+` 委托
   `scheduler-plan-application.service.ts`，其 `approvePlanV2` 实现中
   检索 `operator / approver / createdBy / self / same / 发起 / 回避` 等关键词**零命中**。
2. **更根本：方案生成人根本不落库**。`ewoh_schedule_plan` 表
   （`server/database/schema.ts:658-686`）只有 `confirmedBy` / `confirmedAt`（审批人），
   **没有 `createdBy` / `operator` 字段**——系统无从知道"这个方案是谁生成的"。
3. 因此"自己生成、自己批准"不仅是可能，而是**结构性必然**：
   即使想加回避校验，当前也没有数据基础。

**修复所需**（供 D-2 参考）：`ewoh_schedule_plan` 增加 `created_by` 列（DB 迁移，
按项目惯例需在 runner 注册多处）+ 生成路径记录操作者 + `approvePlanV2` 增加回避校验/审计告警。
预估 1–2d，**建议列入 Next**（安全相关治理，优先级高于 J2）。

## 3. 两个方案

### 案 A：把调度方案接入 approvals 会签系统

在 `APPROVAL_ROLE_POLICY` 登记 `scheduling_plan`（如 `['workshop_lead', 'safety_admin']`），
方案生成后创建会签实例，走多角色逐步审批。

| 维度 | 评估 |
|------|------|
| 收益 | ① 排产方案获得多人复核，降低单人误判；② 若审批独立性缺失属实，可一并修复；③ 与 task/dangerous_action 治理口径统一 |
| 成本 | **高**：扩展白名单 + 方案生成流程改造 + 新增会签 UI + 现有"审批通过"按钮下线或改造 |
| 风险 | ① **改变调度员既有工作方式**，车间排产时效敏感，会签可能拖慢响应；② 涉及流程治理，需业务方共识；③ 与对象工作台 PRD 范围叠加，稀释价值验证 |
| 依赖 | 需先核实 §2 的发起人回避校验 |

### 案 B：本次不接入，维持现状（**推荐**）

对象工作台 PRD 范围内不动方案审批流程；将"审批独立性"作为独立议题立项。

| 维度 | 评估 |
|------|------|
| 收益 | ① 不阻塞对象工作台开工；② 不引入工作方式变更风险；③ 范围清晰，价值可验证 |
| 成本 | 无额外成本 |
| 风险 | 治理问题延后解决（但不因本次改动而恶化） |
| 依赖 | 无 |

---

## 4. 推荐：案 B（本 PRD 范围内不接入）

**四条理由**：

1. **范围纪律**：对象工作台 PRD 聚焦"对象可辨识 + 跨页闭环"，接入会签属于**流程治理**议题，两者混做会让成功标准变得模糊——上线后无法区分效果来自哪部分。
2. **时效敏感**：车间排产对响应速度要求高，会签会延长决策链路。这个代价是否可接受，需要业务方而非产品单方判断。
3. **治理问题性质不同**："自己生成自己批准"若属实，是**内控缺陷**，应作为合规议题独立立项、单独定级，不应搭便车塞进功能迭代。
4. **不阻塞**：无论案 A 还是案 B，对象工作台的 OD-1~OD-7 均可推进（见 §5）。

**推荐动作**：本 PRD 选案 B；同时**立即启动 §2 的后端核实**，若确认审批独立性缺失属实，
则按治理议题单独立项（优先级依合规要求定，可能高于本 PRD）。

## 5. 为什么本决策不阻塞对象工作台开工

| PRD 任务 | 是否依赖本决策 | 说明 |
|---------|--------------|------|
| OD-1 对象描述符 | ❌ 不依赖 | 服务于 `control_request` 等**现有**白名单类型 |
| OD-2 / OD-3 工作台骨架 | ❌ 不依赖 | 首批接 `scheduling_plan`，但走 `getPlan` 只读路径，不涉及审批 |
| OD-4 审批台接入 | ❌ 不依赖 | 服务现有三类审批 |
| OD-5 终态行动条 | ❌ 不依赖 | 与审批流程无关 |
| OD-6 / OD-7 | ❌ 不依赖 | — |

**关键区分**：对象工作台的**首批对象**（`scheduling_plan`，只读视图）与
描述符的**首批服务对象**（`control_request`，审批台）可以不同——
二者通过契约关联，但落地节奏解耦。这正是本决策不阻塞的原因。
